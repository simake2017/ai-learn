## 一、测试方法

1. 设计 5 个不同维度的测试用例：算法实现、代码 Debug、逻辑推理、简单问答、系统设计。
2. 同一 prompt 依次发给三个模型（`max_tokens=1200`，超时 180s），记录：
   - **响应时间**（秒）
   - **输出 token 数**（含思考链，由 usage.completion_tokens 统计）
   - **答案质量**（人工评价：准确性、针对性、是否啰嗦）
3. 每个用例标注"考点"，即该维度预期哪个模型占优。

## 三、具体任务与差异分析

### 用例 1：LRU 缓存实现（算法基本功）

**Prompt**：用 C++ 实现 LRU 缓存，get/put 都是 O(1)，给出完整代码和关键思路说明。

| 模型 | 表现 |
|---|---|
| qwen3-coder-plus ✅ | 18s 完成。哈希表+双向链表方案标准规范：虚拟头尾节点、析构函数释放内存、中文注释清晰，代码可直接编译，无任何废话。 |
| qwen3.8-max | 84s，输出 4761 tok。实现同样正确，但附带大量解释性文字，篇幅约为 coder 的 4 倍。 |
| qwen3.7-flash | 37s，4787 tok。正确，但思考链占据大量 token，正文表达与 coder 相比不够紧凑。 |

**差异点**：三者都能写对，区别在于 coder **又快又紧凑**，工程产出"刚刚好"；max 倾向于长篇讲解；flash 的思考链拖慢了速度。

### 用例 2：迭代器失效 Debug（找 bug）

**Prompt**：找出 `for` 循环中 `v.erase(it)` 的经典 bug 并修复。

| 模型 | 表现 |
|---|---|
| qwen3-coder-plus ✅ | **5.1s、仅 337 tok**。一针见血指出迭代器失效问题，直接给出两个修复方案（`erase()` 返回值写法 + `std::remove_if` 惯用法），后者更高效。 |
| qwen3.8-max | 46s。分析正确且深入（还指出了 `++it` 跳元素的问题），但展开成教学长文，分了 Bug1/Bug2 多个章节。 |
| qwen3.7-flash | 21s。答案正确，篇幅介于两者之间。 |

**差异点**：这是 coder 模型优势最明显的场景——**定位精准、方案专业（知道 remove_if 惯用法）、不拖泥带水**。max 像教科书，coder 像资深工程师。

### 用例 3：狼羊白菜过河（多步约束推理）

**Prompt**：给出完整过河步骤并解释唯一最优解结构。

| 模型 | 表现 |
|---|---|
| qwen3-coder-plus ✅ | 8.7s。7 步方案完全正确，从"最少步数论证、关键约束、唯一性证明、状态转换必然性"四个角度论证，结构清晰。 |
| qwen3.8-max | ❌ **超过 180s 超时**。推测思考链过长导致在限定时间内无法产出最终答案。 |
| qwen3.7-flash | 31.6s，4081 tok。答案正确，但思考链占了绝大部分。 |

**差异点**：本用例原本设计为"旗舰 max 的推理主场"，结果 **max 反而超时**——说明 max 的深度思考在简单问题上会过度展开，得不偿失；coder 的克制输出反而最可靠。

### 用例 4：字符串反转（简单任务）

**Prompt**：Python 一行代码反转字符串。

| 模型 | 表现 |
|---|---|
| qwen3-coder-plus ✅ | 1.1s，给 `s[::-1]` 并附一句切片原理说明。 |
| qwen3.8-max | 1.4s，仅代码块。 |
| qwen3.7-flash | **6.3s、597 tok**——一行代码的问题思考了近 600 token，速度最慢。 |

**差异点**：简单任务上 flash **没有任何速度优势**，思考链反而成为负担。结论：flash 不适合做"小快模型"槽位。

### 用例 5：短链接服务设计（系统架构）

**Prompt**：设计 bit.ly 式短链服务，日写 100 万/读 1 亿，500 字内给出 ID 生成、存储、缓存、权衡。

| 模型 | 表现 |
|---|---|
| qwen3.8-max ✅ | 26s。方案最全面：号段模式发号器、短码复用去重、分库分表阈值、缓存穿透/击穿防护（空值缓存+布隆过滤器+互斥锁）、自增 vs 随机码权衡，工程细节最多。 |
| qwen3-coder-plus | 7.7s，仅 357 tok。给出核心框架但细节明显偏少，偏"提纲式"。 |
| qwen3.7-flash | 21s。意外地完整：改进型 Snowflake、Cache-Aside、三重权衡分析，质量不输 max。 |

**差异点**：**这是 max 唯一明显胜出的场景**——需要广度+深度的架构设计，max 覆盖面最全。flash 在此类结构化问题上表现超出其"轻量"定位。coder 追求简短，牺牲了细节。

## 四、结论与选型建议

### 各模型画像

| 模型 | 画像 | 优势 | 劣势 |
|---|---|---|---|
| **qwen3-coder-plus** | 资深工程师 | 编程任务最快最省；Debug 一针见血；输出紧凑可直接使用 | 架构类回答偏简，广度不足 |
| **qwen3.8-max** | 技术专家/顾问 | 系统设计、复杂权衡覆盖最全；解释最深入 | 慢（3-10 倍于 coder）；简单问题过度思考甚至超时 |
| **qwen3.7-flash** | 爱思考的实习生 | 结构化问题上质量不差 | 思考链导致 token 消耗最高、速度不占优；"flash"名不副实 |

### Claude Code 槽位配置建议（已生效）

| 槽位 | 模型 | 理由 |
|---|---|---|
| 主模型 / Opus / Sonnet | qwen3-coder-plus | 日常编程主力，快、准、省 |
| Opus 兜底（`/model` 切换） | qwen3.8-max | 复杂架构/疑难问题深度分析时用 |
| Haiku / 小快模型 | ~~qwen3.7-flash~~ → 建议 qwen-turbo | flash 测试中简单任务反而最慢，turbo 更符合"轻快"定位 |

### 经验法则

1. **默认用 coder-plus**：编程、Debug、代码解释场景它全面占优。
2. **复杂架构/广度问题切 qwen3.8-max**：系统设计、方案权衡、需要"想全"的场景。
3. **别被 flash 的名字骗**：它的思考链让简单任务变慢变贵，不如 turbo。
4. **token 消耗 ≈ 思考深度**：max 和 flash 的输出里大量是思考链；coder 的输出几乎全是"净内容"，同样预算下有效信息密度最高。
